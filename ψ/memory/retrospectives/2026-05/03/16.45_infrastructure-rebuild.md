## Key Architecture Decisions

1. **pgvector → postgres:16-alpine** — Removed pgvector extension since qdrant handles all vector ops. Simpler, lighter image.
2. **Container names = service names** — `ai-db` → `postgres`, all names are self-explanatory now.
3. **Svix over webhook.site** — API-first, self-hosted, production-grade retry/delivery tracking.
4. **Shared postgres** — Svix uses same postgres with separate `svix_db` database, not a new container.
5. **OpenKB API as custom container** — Wraps openkb CLI with FastAPI for REST access. Uses Ollama qwen3:8b for LLM.
6. **Cloudflare Tunnel for Svix only** — Internal services don't need external access. Only Svix needs webhook.doctorboyz.com.
7. **openkb-api chat uses Ollama directly** — Not through openkb CLI. Gives proper multi-turn chat via OpenAI-compatible API.

## Honest Feedback

Three friction points I need to call out:

1. **I didn't anticipate the orphan container problem.** The migrate.sh script does `docker compose down` but the old ai-db was created by a previous compose file and wasn't tracked by the current one. I should have added `--remove-orphans` to the compose up command, or at least warned about it. Instead, I had to manually intervene. This is a gap in the migration script.

2. **The .env management was sloppy.** I wrote a .env.example with all the new variables, but I didn't properly merge them into the existing .env. The migrate.sh script was supposed to generate secrets, but it only handles the "change_me" pattern — it doesn't add entirely missing keys. I ended up manually editing .env, which is error-prone and not reproducible.

3. **I didn't test the openkb-api container thoroughly.** It starts and responds to /health, but I didn't actually test uploading a document or running a query. The openkb CLI has many dependencies (litellm, markitdown, onnxruntime) that could have runtime issues. I should have done at least one end-to-end test before declaring success.

## Lessons Learned

1. **Orphan containers must be handled in migration scripts.** Always use `docker compose up -d --remove-orphans` when changing service names or removing services.
2. **.env management needs explicit merging, not just examples.** Future migrations should compare .env.example with existing .env and add missing keys with generated secrets.
3. **End-to-end testing after infrastructure changes is essential.** Just because containers start doesn't mean they work. Test each new service's API endpoint.
4. **Webhook infrastructure (Svix) only needs external tunnel for receiving webhooks from outside.** Internal services communicate through Docker network — no tunnel needed.
